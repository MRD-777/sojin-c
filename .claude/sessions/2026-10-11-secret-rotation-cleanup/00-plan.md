## المشكلة

مفتاح `service_role` قديم اتسرّب في ريبو public واتقفل. بعده:
1. المفتاح الحالي (`sb_secret_…`، 41 حرف) **ظهر في transcript** — يعني مكشوف هو كمان.
2. السكربتان `create-demo-users.mjs` و`smoke-auth.mjs` فيهم **مفاتيح وباسوردات مدفونة**.
3. `BACKLOG.md` فيه **باسوردات الديمو** (سطر 352 · 363).
4. **مفيش طريقة push** من البيئة دي (لا credentials، لا `gh`).
5. session الـ autonomous-harness **مفتوحة بلا إقفال**.

## التحليل — الجذر

**الجذر مش «مفتاح اتسرّب» — الجذر إن المفتاح كان له مصدران.**
قيمة واحدة (مفتاح الـ service-role) عاشت في **مكانين**: `.env` (محمي) و**مدفونة
في سكربت متتبَّع في الجيت** (مكشوف). طول ما فيه مصدر تاني، حماية الأول بلا معنى.

⇒ الإصلاح **توحيد المصدر** (`.env` وحده) + **بوابة تمنع العودة** (السكربت يفشل
بصوت عالٍ بدل ما يشتغل بقيمة مدفونة). **ونفس عائلة `P-1`** (حقيقة بمصدرين).

## الحل المقترح

### 🔴 المرحلة 1: Deploy key — **أولاً، لأنها بتفتح شغل متوازٍ لك**
**الملفات:** `~/.ssh/` + `.git/config` (**غير متتبَّعين — صفر أثر على الريبو**)

1. `ssh-keygen -t ed25519 -f ~/.ssh/sojin_c_deploy -N "" -C "sojin-c-deploy-$(date +%F)"`
   — اسم **مخصوص للريبو ده**.
2. `~/.ssh/config` بـ **Host alias** مقيَّد:
   ```
   Host github-sojin
     HostName github.com
     User git
     IdentityFile ~/.ssh/sojin_c_deploy
     IdentitiesOnly yes
   ```
   `IdentitiesOnly yes` بيمنعه يجرّب أي مفتاح تاني.
3. `git remote set-url origin git@github-sojin:MRD-777/sojin-c.git`
   — **الـ alias بيضمن إن المفتاح ده للريبو ده بس** (شرطك).
4. **أطبع `.pub` وحده.** المفتاح الخاص **ما يُقرأ ولا يُطبع ولا يُنسخ** — ولا مرة.

**الـ Risks / تحذيرات لازم تعرفها:**
- 🔴 **لازم تفعّل «Allow write access»** عند إضافة الـ deploy key في GitHub
  (Settings → Deploy keys → Add). **بدونها الـ push هيرفض** وهنلف تاني.
- 🔴 **الحاوية دي مؤقتة** — المفتاح الخاص **بيموت معاها**. ⇒ **بعد ما الـ PR
  يتفتح، امسح الـ deploy key من GitHub**؛ سيبانه = مفتاح write بلا حائز.
- الـ remote بيتحوّل لـ SSH؛ `.git/config` **مش متتبَّع** فمفيش أثر في الـ diff.

### المرحلة 3: `.env` — فرعان حسب جوابك
**الملفات:** `apps/api/.env` (مستبعَد من الجيت — مُتحقَّق)

**الحالة القائمة المُتحقَّق منها:** سطر واحد بالظبط
(`grep -c "^SUPABASE_SERVICE_ROLE_KEY=" = 1`)، القيمة `sb_secre…` بطول **41**.

- **فرع (أ) — لو `sb_secret_2EZZ…` هو `backend`:**
  **صفر تعديل.** القيمة **بالفعل** في `SUPABASE_SERVICE_ROLE_KEY`. المرحلة
  تتحوّل لـ **تحقق فقط** (سطر واحد + prefix + length).
- **فرع (ب) — لو هو `default`:**
  أستلم `backend` في رسالة لوحده ⇒ **أبدّل السطر** (أعيد بناء الملف، مش append)
  ⇒ `grep -c` = 1 قبل وبعد ⇒ أطبع **prefix(8) + length** بس.

**الـ Risks:** `sed -i` في المكان على سطر فيه `/` أو `&` بيتعطّب ⇒ **إعادة بناء
الملف بـ `awk` أأمن من `sed`**. والتحقق `grep -c`=1 **قبل وبعد** بيمنع «سطر زيادة».

### المرحلة 4: تنظيف السكربتين
**الملفات:** `apps/api/scripts/create-demo-users.mjs` · `smoke-auth.mjs`

**(أ) `create-demo-users.mjs`:**
- `URL` ⇒ `process.env.NEXT_PUBLIC_SUPABASE_URL`
- `SERVICE_KEY` ⇒ `process.env.SUPABASE_SERVICE_ROLE_KEY` (**service-role مطلوب
  فعلاً** — `auth.admin.listUsers` / إنشاء مستخدمين)
- الباسوردان ⇒ `process.env.DEMO_ADMIN_PASSWORD` / `DEMO_CLIENT_PASSWORD`
- **بوابة فشل:** أي متغير غايب ⇒ رسالة فيها **اسمه** + `process.exit(1)`

**(ب) `smoke-auth.mjs`:**
- `ANON` ⇒ **`process.env.SUPABASE_SMOKE_KEY`** — **بلا أي default** (شرطك)
- `password` ⇒ `process.env.DEMO_ADMIN_PASSWORD`
- **كومنت إلزامي جوّه السكربت** (شرطك):
  > *«`SUPABASE_SMOKE_KEY` لازم يكون **publishable** (`sb_publishable_…`) لا secret.
  > تسجيل الدخول `signInWithPassword` **مايحتاجش service-role** — ده مسار مستخدم
  > عادي. حطّ مفتاح secret هنا = صلاحية admin في سكربت اختبار بلا أي داعٍ.»*
- **بوابة فشل** بنفس الشكل

**الـ Risks:**
- 🔴 **`sb_publishable_` مش موجود عندك لسه** — أنا نصحتك قبل كده إنك مش محتاجه
  (لأن الويب مش بيستخدم Supabase). ⇒ **`smoke-auth.mjs` هيفشل فشلاً نظيفاً**
  لحد ما تعمل publishable key. **ده السلوك المقصود لا عيب** — بس **اعرفه مقدماً**
  عشان ما يُقرأ كـ regression.
- الـ `URL` **مش سرّ** (موجود في `.mcp.json` وفي `NEXT_PUBLIC_*`) — بينتقل للـ env
  **للنقلية لا للسرّية**، ويُقال كذلك في التقرير.

## نقاط القرار

### 🔴 1 — سؤال واحد غير محسوم: الـ bracket فاضي
كتبت: **«المفتاح `sb_secret_2EZZ…` هو [backend / default]»** — **والقوسان
ما اتعبّوش**. مش هخمّن: الفرق بيحدد هل المرحلة 3 **تحقق فقط** ولا **تبديل سطر**.

**محتاج كلمة واحدة: `backend` ولا `default`؟**
(ولو `default` ⇒ ابعت `backend` في رسالة لوحده.)
**مينفعش أعرفها بنفسي** — الـ Management API محتاج token مش موجود، وشكل المفتاح
مافيهوش اسمه.

### 2 — حسم النقطة (5) بتوصيتي، كما أذنت
**السؤال:** نحجب الـ JWTs القديمة من تقارير الـ sessions التاريخية؟
🔴 **توصيتي: لا — وتُعلَن استثناءً معروفاً في الـ scan.** الأسباب:
1. المفاتيح **معطَّلة فعلاً** ⇒ الخطر التشغيلي صفر.
2. **تقارير الـ sessions سجل تدقيق.** تحريرها بأثر رجعي **بيزيّف السجل** —
   وده عيب أخطر على مشروع قيمته كلها في أمانة سجله.
3. الـ scan هيفضل بيطلّعها ⇒ **تُسجَّل كـ allowlist مُبرَّر، مش تُخفى.**

### 3 — بنود للعلم لا للقرار
- **`smoke-auth.mjs` هيفشل** لحد ما تعمل `sb_publishable_` (المرحلة 4).
- **امسح الـ deploy key من GitHub بعد الـ PR** — مفتاحه الخاص بيموت مع الحاوية.
- **«Allow write access»** إلزامية وقت إضافة الـ deploy key.
