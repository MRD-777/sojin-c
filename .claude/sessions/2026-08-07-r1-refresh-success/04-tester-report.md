### M0 — الشاهد السالب: **أهم نتيجة في التقرير**

**لماذا أضفتها رغم إنها مش في الجدول:** الخطة ادّعت إن السطر 101 **متجاوَز**، وإن تعطيله
هيسيب الـ spec أخضر ⇒ **mutation كاذبة**. الادّعاء ده كان **استنتاجاً من قراءة الكود
لا قياساً**. وبند بيقول «الهدف ده كاذب» **لازم يتقاس** وإلا بنكون استبدلنا ثقة بثقة.

```
[client.ts:101 محذوف]

      Tests  4 passed (4)
```

**⇒ مُثبَت تجريبياً: تعطيل السطر 101 لا يُسقط أي spec.** `WEB-S2-TOKENDUP-001` مش
ملاحظة نظرية — **الهدف الأوضح للـ mutation هو فعلاً هدف كاذب**، ولو المختبر تبع حدسه
بدل الجدول المُثبَّت كان **هيكتب في التقرير إن MVT-1 «بيعضّ» وهو ما عضّش**.

**الدرس الأعم:** لما يبقى في **مساران** بيوصّلوا نفس الأثر (سطر 101 و store→interceptor)،
الـ mutation على الأضعف بترجع خضراء وتُقرَأ كـ «مغطّى». **تعدّد المسارات بيخلّي
الـ mutation نفسها تحتاج شاهداً سالباً.**

### M1 — 🔴 **F-1: سقوط جانبي غير متنبَّأ به** (بلاغ صريح، قاعدة #5ب)

```
× MVT-1 → expected 'Bearer OLD_TOKEN' to be 'Bearer NEW_TOKEN'
× MVT-4 → expected [ 'Bearer OLD_TOKEN', …(2) ] to deeply equal [ 'Bearer NEW_TOKEN', …(2) ]
 Test Files  1 failed | 14 passed (15)
      Tests  2 failed | 46 passed (48)
```

الخطة تنبّأت «MVT-1 وحده». **الواقع: MVT-1 + MVT-4.** بلّغته كما تفرض القاعدة، **وفحصته
بدل ما أكتفي بتسجيله** — والتفصيل بيغيّر الحكم:

**أي تأكيد في MVT-4 هو اللي سقط؟** ترتيب تأكيدات MVT-4 بعد فتح البوابة:
(1) `refreshSpy` مرة واحدة → (2) `count === 6` → (3) الـ payloads → (4) `authHeaders`.
رسالة الفشل على **الرابع**، يعني **الأول نجح**.

> 🔴 **الحكم: اقتران في نطاق التأكيدات، لا في المفهوم.**
> **التأكيد الأساسي لـ MVT-4 (مكافحة الـ stampede) نجا من M1 سليماً** — اللي سقط هو
> تأكيد **مساعد** بيتقاطع مع مفهوم MVT-1. والدليل الحاسم على إن المفهومين منفصلين هو
> **M3**: كسر الـ singleton أسقط **MVT-4 وحده** ولم يمسّ MVT-1 إطلاقاً. لو المفهومان
> مقترنان فعلاً، كان M3 لازم يسقّط الاتنين.

**⇒ M1 و M3 معاً بيثبتوا الفصل المفاهيمي**، والاقتران محصور في التأكيد الرابع.

**قراري: لا أحذف التأكيد الرابع.** «كل الـ retries المتزامنة حملت التوكن الجديد» خاصية
**أقوى** من نظيرتها في MVT-1 (اللي بتغطّي طلباً واحداً): هي اللي بتمنع سيناريو «الأول
بياخد الجديد والباقي بيتعادوا بالقديم». **حذفها لتحسين نظافة الـ mutation = تضحية
بتغطية حقيقية إرضاءً لمعيار إجرائي.** البديل الصح إن الاقتران **مُعلَن** — وهو ده
اللي بيحصل هنا.

**الخطأ الحقيقي كان في الخطة لا في الـ specs:** الخطة صنّفت الـ specs بـ «الغرض» وتنبّأت
بالسقوط على أساسه، بينما الـ mutation بتضرب **التأكيدات** لا الأغراض. المطلوب مستقبلاً:
**تنبّؤ على مستوى التأكيد لا على مستوى الـ spec.**

### M2 — مطابق تماماً + إغلاق البند المُسلَّم #4

```
× MVT-2 → expected undefined to be true
× MVT-3 → expected { code: 'UNKNOWN', …(1) } to match object { code: 'UNAUTHORIZED' }
 Test Files  1 failed | 14 passed (15)
      Tests  2 failed | 46 passed (48)
```

MVT-2 + MVT-3 **وحدهما**. MVT-1 و MVT-4 نجيا ⇒ **صفر اقتران زائف في M2.**
الاقتران المُعلَن سلفاً صحيح: الآلية (`_retry` واصل الـ transport) والسلوك (retry واحد)
**نفس القيد على عمقين**.

**⚠️ ملاحظة على شكل فشل MVT-3 — لافتة:** MVT-3 **ما سقطش** برسالة `LOOP:`. سقط على
`code: 'UNKNOWN'` بدل `'UNAUTHORIZED'`. السبب: الـ `LOOP:` throw بيطلع خطأ **بلا
`.response`**، فـ `mapAuthError` بيرجّع الـ fallback `UNKNOWN`. يعني **آلية الأمان
اشتغلت لكنها اتخفّت وراء `mapAuthError`** — والـ spec اتمسك بتأكيد تانٍ.

**البند المُسلَّم #4 — دليل مباشر (probe مؤقت، اتحذف بعد القياس):**

```
[تحت M2]        PROBE_RESULT transportCalls=3 loopGuardFired=true  msg=LOOP: transport called 3 times, expected 2
[بلا أي طفرة]   PROBE_RESULT transportCalls=2 loopGuardFired=false msg=null
```

⇒ تحت M2 الـ retry **رجع فعلاً لمحاولة ثالثة**، والـ `LOOP:` guard **هو اللي وقّفه**.
بلا الطفرة: محاولتان بالظبط، والحارس **ما اشتغلش**. **البند #4 مقفول بقياس، لا باستنتاج.**
