## §1 — الجواب على السؤال الأول: هل انحراف (أ) مقبول؟

### ✅ مقبول — بل كان **إلزامياً**، والخطة هي اللي غلطت مش المبرمج.

الخطة نصّت على الفروع التلاتة في الـ interceptor وسابت الـ `catch` بتاع الـ refresh
بدون ذكر. ده **مش سكوت محايد — ده ثقب في الخطة**، لأن الـ `catch` ده بالظبط هو
المكان اللي فيه الحالة التالتة أكتر احتمالاً: الـ refresh بيتنادى وقت ما الـ access
token ميت، وده أكتر وقت الـ API فيه بيكون بيعمل restart في الـ dev.

الاختبار الحاسم: **هل الانحراف بيخدم قاعدة الـ session ولا بيخترقها؟**

> القاعدة: **الـ 401 المُثبَت وحده هو اللي بيقتل الجلسة.**

الكود القديم في الـ `catch` كان بيقتل الجلسة على **أي** فشل — بما فيه انقطاع
الشبكة. سيبه كان معناه إن الـ session تقفل الحلقة في المسار الرئيسي وتسيبها
مفتوحة في مسار الاستثناء. **الانحراف بيوسّع تطبيق القاعدة، مش بيستثني منها.**

وده بالظبط سلوك المبرمج المطلوب في CLAUDE.md: لقى حاجة مش في الخطة، **ما سكتش
وما نفّذهاش بصمت** — نفّذ وبلّغ بحدّ الدقة مكتوباً في التقرير **وفي الكود نفسه**
(`client.ts:130-134`). الشفافية هنا أعلى من المطلوب.

**تصحيح ذاتي (المخطط):** الميزانية اللي حطيتها (5 specs) اتكتبت **قبل** ما
الانحراف ده يوجد. النتيجة إن فرع كامل جديد في `client.ts` شحنه المبرمج بـ
**صفر MVT**، وده يخالف قاعدة #2 ("1 test لكل fix"). الخطأ خطأي — تصحيحه في §5.

## §2 — الجواب على السؤال التاني: الـ gap يتقفل هنا ولا يترفع؟

### 🔴 يُقفَل هنا. الإرجاء مرفوض — لثلاثة أسباب، التالت هو الحاسم.

#### (1) الفرضية المعمارية في البند **غلط**: مفيش داعي نلمس `auth-client.ts` أصلاً

المبرمج كتب: *"تعديل `auth-client.ts` ليحافظ على الـ status = قرار معماري"*.
لكن `auth-client.refresh()` مش بيبني الخطأ بنفسه — بيفوّضه:

```ts
// auth-client.ts:78
catch (e) { throw mapAuthError(e); }   // e = الـ AxiosError الخام، الـ status جوّاه
```

يعني الـ status **بيوصل لـ `mapAuthError` سليماً** وبيتضيّع **جوّه** `mapAuthError`،
مش في `auth-client`. فالإصلاح حقله `map-auth-error.ts` — وهو **ملف داخل قائمة
تأثير الخطة الأصلية** (`00-plan.md`، جدول "التأثير على الـ Codebase")، ومعدَّل
في الـ session دي أصلاً.

⇒ **البند مش خارج النطاق. هو جوّه النطاق، واتحسب بره غلطاً.**
الحاجز اللي خلّى المبرمج يرجّعه لي (لمس ملف تالت) **مش موجود**.

#### (2) الفجوة بتصيب **الخطر اللي الخطة نفسها سمّته بالاسم**

من `00-plan.md` §المرحلة 1 / الـ Risks:

> *"429 مهم: أثناء عاصفة الحلقة الـ refresh بيتخنق (30/min في `auth.controller.ts:109`).
> لو 429 اتحسب `terminal` هنطرد المستخدم بسبب ازدحام إحنا اللي عملناه."*

مُتحقَّق منه في الكود الآن: `auth.controller.ts:107` عليها
`@Throttle({ auth: { limit: 30, ttl: 60_000 } })`. والمسار الحالي:

```
429 من /auth/refresh
  → authClient يرمي { code: "AUTH_..."/"UNKNOWN" }   ← مش "NETWORK"
  → isTransportFailure === false
  → terminateSession()  ⇒ logout كامل
```

يعني الخطر اللي الخطة كتبته بخط أحمر **مقفول في المسار الرئيسي ومفتوح في مسار
الـ refresh**. والأسوأ: الـ 502 من proxy برد HTML بلا envelope بيدخل
`mapAuthError` ويطلع `code: "UNKNOWN"` — فبنطرد المستخدم على خطأ **اسمه
حرفياً "غير معروف"**. ده تناقض مباشر مع نص التعليق في `refresh-policy.ts:28`:
"ONLY A PROVEN 401 KILLS A SESSION".

#### (3) 🔴 الحاسم: `catch` فيه **نسخة تانية أضعف من نفس القاعدة**

ده مش نقص تغطية — ده **ازدواج قرار**. دلوقتي فيه حكمين على نفس السؤال:

| الموقع | الشكل | المجال |
|---|---|---|
| `refresh-policy.ts` | `classifyFailure` | **تلاتي** ✅ |
| `client.ts:135-141` (الـ catch) | `isTransportFailure` boolean | **ثنائي** ❌ |

الـ boolean ده **هو بالظبط خطأ التصنيف اللي `00-plan.md` §رابعاً بناها كلها عليه**
("الكود عنده حالتين لمجال فيه تلاتة")، ناجياً في طبقة أعمق بشكل شبه مطابق.

> **ولاحظ الشكل:** الخرق سكن في **الاستثناء الشكلي** — الـ `catch` وسط دالة
> اتعادت هيكلتها بالكامل — مش في القاعدة. ده نفس النمط اللي قاعدة #5أ بتوصفه.
> لو ترحّل، الـ session هتقفل بتقرير بيقول "الحالة التالتة اتمثّلت" والحقيقة
> **اتمثّلت في مكانين من تلاتة**.

#### الإصلاح المعتمد — يستهلك القاعدة الواحدة بدل ما ينسخها

**(أ) `map-auth-error.ts`** — حقل اختياري + تعبئته من المصدر:
```ts
export interface AuthError {
  // ...
  /** HTTP status when a response came back; undefined on transport failures. */
  status?: number;
}
// في فرع الـ envelope: status: err.response?.status
// (فرع NETWORK يسيبه undefined عمداً — وده المُدخَل الصح لـ classifyFailure)
```
⚠️ `AxiosLikeError.response` لازم تتوسّع لـ `{ data?: unknown; status?: number }`.

**(ب) `client.ts` — الـ catch يستدعي نفس الدالة، والـ boolean يتشال:**
```ts
} catch (refreshError) {
  const disposition = classifyFailure({
    status: (refreshError as AuthError | undefined)?.status,
    alreadyRetried: false,
    isRefreshCall: true,          // ← ده بالظبط الـ flag اللي الحقل موجود عشانه
  });
  if (disposition === "terminal") terminateSession();
  return rejectMapped(refreshError as AuthError, disposition);
}
```
`isRefreshCall: true` بيدي: 401 ⇒ `terminal` ✅ · 429/5xx/undefined ⇒ `indeterminate` ✅
· و`"refresh"` **غير قابل للإنتاج** من هنا. القاعدة واحدة في مكان واحد،
والـ `refresh-policy` بقى الحكم الوحيد فعلاً مش اسماً.

**أثر جانبي مقصود:** `unwrap` لو رمى على envelope مشوّه ⇒ status undefined ⇒
`indeterminate`. صح: رد ناجح مشوّه **مش دليل** على جلسة ميتة.

#### §2ب — البند #8 (اكتشاف المخطط): `mapAuthError` بتتنادى مرتين

`rejectWith` (`client.ts:95-98`) بتعمل `mapAuthError(error)` على `refreshError` —
وده **مخطوط بالفعل** من `auth-client.ts:78`. تتبُّع المُدخَل `{ code:"NETWORK", message:"تعذّر الاتصال…" }`:

| خطوة في `mapAuthError` | النتيجة |
|---|---|
| `err.response?.data` | `undefined` ⇒ فرع الـ envelope **مش بيتاخد** |
| `err.request !== undefined` | `false` ⇒ فرع NETWORK **مش بيتاخد** |
| fallthrough | **`{ code: "UNKNOWN", message: "حدث خطأ غير متوقع — حاول مجدداً" }`** |

⇒ على كل مسارات فشل الـ refresh، الـ `code` والـ `message` اللي بيوصلوا للمستدعي
**بيتمسحوا**. المستخدم بيتقاله "خطأ غير متوقع" بدل "مشكلة اتصال" — في المسار
اللي الـ session دي كلها عن التمييز بينه وبين غيره.

- **قِدَم:** ⚠️ **pre-existing** — الـ baseline كان `Promise.reject(mapAuthError(refreshError))`
  (مؤكَّد من `git diff`). الـ session **ما أدخلتوش**، لكنها **ما شفتوش** وهي واقفة فوقه.
- **الخطورة:** 🟡 MEDIUM-LOW. الـ `sessionDisposition` بيتحط **بعد** الـ map فبينجو
  ⇒ **كسر الحلقة مش متأثر**، والـ RouteGuard بيقرأ الـ disposition مش الـ `code`.
  الضرر على نص الخطأ + أي مستهلك مستقبلي بيـ special-case الـ `code` (زي الـ lockout).
- **الإصلاح:** `rejectMapped(mapped: AuthError, d)` صريحة تختم بدون إعادة map.
  ❌ **ممنوع** حلّها بجعل `mapAuthError` "idempotent" بتخمين شكل المُدخَل —
  normalizer أمني ما بيشتغلش بالـ heuristics؛ المستدعي هو اللي يعرف إن مُدخَله مخطوط.
- **ليه دلوقتي:** نفس 5 سطور، نفس الـ `catch`، ونفس الـ specs الجديدة هتغطي الاتنين.

#### 🔒 فحص شرط الترقية لـ Deep — على الإصلاح المقترح

| الشرط | الحالة |
|---|---|
| `decide-redirect.ts` / `middleware.ts` | ❌ لا تعديل |
| توقيت **وضع** `auth_hint` | ❌ لا تعديل |
| `apps/api` | ❌ لا تعديل |
| اتجاه التغيير | teardowns **أقل** — مفيش مسار بيكسب صلاحية |

الجلسة الناجية بتحتفظ بـ access token **الـ API نفسه هيرفضه بـ 401** لو باطل
⇒ ساعتها `terminal` بالقاعدة. البوابة الحقيقية (JWT guard) ما اتلمستش.
⇒ **مفيش ترقية. نفضل Standard.**

## §3 — انحرافات (ب) و (ج)

### (ب) فرع `refresh` بدون `config` ⇒ `indeterminate` — ✅ **قُبل، وهو أدق من الخطة**
الكود القديم `if (willRefresh && config)` كان بيسيب الحالة دي تقع في الـ
fallthrough وتنتهي عند `if (status === 401) terminateSession()` ⇒ **teardown على
401 إحنا أصلاً ما جربناش نعالجه**. التحديد الصريح صح: مفيش request نقدر نعيده
= ما وصلناش نختبر الجلسة. والأهم إنه اتكتب كـ `return` مبكر بدل شرط مركّب —
فالحالة بقى ليها اسم بدل ما تكون فراغاً بين شرطين.

### (ج) 5 مفاتيح i18n بدل "مفتاحين" — ✅ **قُبل بالكامل**
"مفتاحين" في الخطة كان **تقديراً** مش قيداً. و`description` في `en.json`:

> *"You are still signed in — this is a connection problem, not a sign-out."*

ده **الإصلاح نفسه معروضاً للمستخدم**. القرار الأساسي في الـ session هو التمييز
بين "مش عارفين" و"ميتة"؛ لو الـ UI ما بلّغش المستخدم بالتمييز ده، هو هيفترض
إنه اتسجّل خروج وهيعمل login تاني — فنكون قفلنا الحلقة تقنياً وسبناها سلوكياً.
النص **حامل للدلالة، مش تزييني**. (`ar.json` كمان — RTL parity محفوظ.)

**ملاحظة للمختبر:** المفاتيح دي في namespace `Common.sessionUnavailable`؛ أي spec
بيـ mount الـ `SessionUnavailable` محتاج `NextIntlClientProvider` بالرسايل، وإلا
`useTranslations` هيرمي والـ spec هيسقط لسبب **مش** اللي بيختبره.

## §4 — الجواب على السؤال التالت: RC-2 في الـ BACKLOG؟

### ✅ أيوه — بس **مش RC-2 نفسه**. الفصل ده هو الجواب.

| البند | الحالة | ليه |
|---|---|---|
| **RC-2 كسبب جذري مستقل** | 🔒 **مقفول نهائياً — بالقياس** | نقطة القرار في المرحلة 3 اتنفّذت زي ما الخطة نصّت: صفر timeouts، الذاكرة 4,166 → 1,457 MB مستقرة، **بدون أي tuning**. فرضية "عرَض مش سبب" **اتأكدت تجريبياً**. تسجيله بيدي إيحاء إن فيه حاجة ناقصة — مفيش |
| **إجراء الاستعادة اللي اكتشفه المبرمج** | 📥 **يتسجّل — dev-hygiene 🟢 LOW** | ده اللي **يستاهل** التسجيل |

**ليه الجزء التاني بالذات:** المبرمج اكتشف أثناء التنفيذ إن قتل الـ dev server
بالـ PID **ما بينفعش** — الـ supervisor (`next dev`) عمل respawn فوراً
(15684 → 6472)، والملفات المقفولة منعت مسح `.next`. ده يفسّر ليه "restart عادي
مش بيداوي الحالة دي" — وهي معرفة **اتشُريت بوقت تشخيص فعلي** ومصيرها الضياع
لو ما اتكتبتش. القيمة مش في RC-2، القيمة في **الإجراء**.

#### النص المقترح للـ `BACKLOG.md`

```markdown

- ❌ قتل الـ PID مش كافي: `next dev` supervisor بيعمل respawn فوراً،
  والملفات المقفولة بتمنع مسح `.next`.
- ✅ الإجراء: اقتل **شجرة** الـ process كلها → امسح `apps/web/.next` → أعد التشغيل.

### NEXT16-001 — `middleware` deprecated لصالح `proxy` 🟡 MEDIUM

  ⇒ أي هجرة **تلمس حدود الأمان** ⇒ **Deep mode إلزامي**، مش Quick.
- 🔴 قبل أي كود: اقرأ `node_modules/next/dist/docs/` (قاعدة `apps/web/AGENTS.md`).
```

## §5 — تصحيح ميزانية الـ MVT (قاعدة #3) — **5 → 7 specs**

الميزانية القديمة اتكتبت قبل انحراف (أ) والبند #8. الفروع الجديدة في الـ `catch`
شُحنت بصفر تغطية. الإضافة:

| # | الملف | البند | الـ assertion الأعمق (قاعدة #4) |
|---|---|---|---|
| **6** | `client.session-liveness.spec.ts` | الـ refresh بيفشل بـ **429** (envelope كامل، مش network) ⇒ **الجلسة تنجو** | `accessToken === OLD` **و** `auth_hint` لسه في `document.cookie` **و** الرفض `sessionDisposition:"indeterminate"` **و** `code` هو كود الـ 429 **مش `"UNKNOWN"`** (← ده اللي بيقتل البند #8) |
| **7** | نفس الملف | الـ refresh بيفشل بـ **401** ⇒ **terminal** (control) | `accessToken === null` **و** `auth_hint` **اتشال فعلاً من `document.cookie`** **و** `code === "UNAUTHORIZED"` محفوظ |

🔴 **6 و 7 لازم يكونوا زوجاً.** لو 6 لوحده، خضاره ممكن يكون لأن الـ teardown
اتكسر في كل الحالات — نفس الحجة اللي رفعت الميزانية من 4 لـ 5 في الخطة الأصلية.

**الـ mutation: 2/5 → 3/7 (مُعلَنة صراحةً)** — يتضاف:

| الـ Spec | التعطيل | المتوقع |
|---|---|---|
| **MVT-6** | رجّع الـ `catch` لـ `terminateSession()` غير مشروط | **MVT-6 وحده يسقط** (MVT-7 يفضل أخضر — هو control على نفس الفرع) |

الـ 4 الباقيين (1، 2، 4، 7) **بلا mutation** — تغطيتهم **غير مُثبَتة** بمعيار
قاعدة #5b، ومنقولة كده صراحةً للمراجع الأعلى.

## تقييم المعمارية

**✅ القوة الحقيقية — الحالة التالتة بقى ليها اسم في **نوع**، مش في تعليق.**
`FailureDisposition` بيخلي الـ compiler يفرض الـ exhaustiveness. لو حد ضاف حالة
رابعة بكرة، الفروع اللي ما بتعالجهاش هتبان في الـ type check مش في production.
ده الفرق بين تصحيح bug و **إقفال فصيلة الـ bug**.

**✅ الـ 4 specs القديمة كـ regression harness** — الخطة قصدت ده، والتنفيذ
حققه حرفياً (صفر تعديل، 4 خضراء). ده أنظف دليل على إن الـ refactor حافظ على
الدلالة القديمة بالكامل.

**✅ الافتراضي الآمن في الاتجاه الصح.** `isSessionProvenDead` بترجع `false`
لأي شكل غير متوقع ⇒ الفشل المجهول بيفشل **ناحية عدم الحركة**. الحلقة محتاجة
**حركة** عشان تتكوّن؛ فالتصميم بيمنع تكوّنها **بنيوياً** لا بشرطياً.

**⚠️ ملاحظة معمارية جديدة (غير حاجبة) — `useMe` عليها `retry: false`.**
النتيجة: أول blip شبكي (ولو 300ms) بيرمي المستخدم على شاشة alert بملء الصفحة.
قبل الـ session: blip ⇒ حلقة (أسوأ). بعدها: blip ⇒ شاشة + زرار Retry (أحسن،
بس مش سلس). `retry: false` **قرار مقصود وموثّق** (الـ interceptor بيملك الـ
retry)، والتعديل بلا تفكير هيأخّر الـ redirect الشرعي على 401. ⇒ **لا تغيير
في الـ session دي.** مرشّح لـ session UX منفصلة: auto-retry محدود **لحالة
`indeterminate` وحدها**.

**⚠️ 403 ⇒ `indeterminate` ⇒ شاشة retry لا تنتهي.** مقصود ومتّسق مع القاعدة
("مصرّح لكن ممنوع" ≠ "جلسة ميتة")، ولا يُتوقَّع حدوثه على `/users/me`. زرار
"تسجيل الدخول" هو مخرج الطوارئ. 🟢 LOW — للتوثيق لا للإصلاح.

**📌 حالة البيئة — للمختبر.** المبرمج شغّل `npx next dev --turbopack` مباشرةً
بدل `npm run dev` (turbo). التأكيد الحي لازم يتعمل على الشكل اللي المستخدم
بيشغّله فعلاً؛ التأكيد على setup مختلف بيقيس بيئة تانية.
