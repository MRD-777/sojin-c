## Attack Vectors المفحوصة

- [x] Authentication bypass — لا سطح جديد (JWT/ES256 عالمي، صفر `@Public` في الـ module)
- [x] Authorization (IDOR، privilege escalation) — **المحور الأول، مفصّل أدناه**
- [x] Input validation (حدود، أعداد، تواريخ، نصوص) — **3 ثغرات**
- [x] Tenant isolation على الـ 3 models الجديدة
- [x] Business logic abuse (تلاعب مالي، نِسب، تضخيم إنجاز) — **ثغرتان**
- [x] Double submit / race conditions (TOCTOU على الحالة والصلاحية)

- [x] Resource exhaustion (عمق الشجرة، N+1، pagination) — **ثغرة**
- [x] Information disclosure (فروق 404/403، projection الـ CLIENT)
- [x] File upload — غير منطبق (الـ module مافيهوش رفع)

## 🔴 المحور 1 — الطبقة 4 كحاجز وحيد ضد خصم داخلي عالي الصلاحية

**الخصم المفترض:** `ACCOUNTANT` شرعي في الشركة، عايز يربط تقرير معتمد من **مشروع آخر في نفس الشركة** ببند BOQ (تضخيم إنجاز بند / نقل قيمة شغل بين مشاريع). الطبقتان 2 و3 لا تعترضانه إطلاقاً (شركة واحدة + ACCOUNTANT بقى company-wide بعد المرحلة 2)، والطبقة 5 لا تُبلَغ.

**محاولات الاختراق:**

| الهجوم | النتيجة |
|---|---|
| `updateId` لتقرير معتمد في مشروع آخر / نفس الشركة | **فشل** — الـ `where` بيشترط `phase.project.id = boqItem.projectId` ⇒ الصف غير موجود ⇒ 404 |
| `updateId` لتقرير في شركة أخرى | **فشل** — `companyId` في نفس الـ `where` |
| تمرير `projectId` أو `phaseId` في الـ body للتحايل | **فشل** — `LinkUpdateDto` فيه `updateId` فقط، و`forbidNonWhitelisted: true` بيرفض أي مفتاح زيادة بـ 400 |
| ربط تقرير `PENDING`/`REJECTED`/`FORCE_CANCELLED` | **فشل** — 400 صريح بعد الـ scoping |
| ربط تقرير تحت **مرحلة محذوفة** في نفس المشروع | **فشل** — `phase.deletedAt: null` |
| ربط تقرير محذوف (soft) | **فشل** — `deletedAt: null` |
| استغلال البند نفسه: `boq/:id` لبند في شركة أخرى | **فشل** — `readItemIn` مقيَّد بـ `project.companyId` ⇒ 404 |

### 🔑 تصحيح لتفكيك المخطط — الطبقتان 2 و4 **مقترنتان، لا مستقلتان**

المخطط وصف الطبقة 2 بأنها لا تُضيف شيئاً ضد الخصم الداخلي. **دقيق ظاهرياً وخطأ عملياً:** قوة الطبقة 4 كلها متوقفة على أن `boqItem.projectId` **مُدخَل نظيف**، ومصدر نظافته هو الطبقة 2 (`readItemIn` مقيَّد بـ `project.companyId`). لو "حُسِّن" الـ read يوماً إلى `findUnique({ id })` — وهو تحسين يبدو بريئاً تماماً ولن تسقط بسببه ولا spec — لظلّت الطبقة 4 تعمل **بإخلاص**: ستقيّد التقرير بـ `boqItem.projectId`… وهو حينها **مشروع مستأجر آخر**. النتيجة: ربط داخل شركة أجنبية عبر بوابة تبدو سليمة.

**الخلاصة الهجومية:** الحاجز الحقيقي مش "الطبقة 4" لوحدها، هو **السلسلة 2→4**. أي spec للـ IDOR لازم يغطي **الطرفين**: (أ) تقرير من مشروع آخر يُرفض، (ب) **بند من شركة أخرى يُرفض قبل ما يوصل للطبقة 4 أصلاً**. تغطية (أ) وحدها تترك الحلقة الحقيقية بلا حارس.

**فحص إضافي — هل الـ link يسرّب تقريراً لا يملك المنادي رؤيته؟** لا. `updates.service.ts:92-110` و`:183-196`: الأدوار الميدانية ترى `own ∪ APPROVED`، والربط يشترط `APPROVED` ⇒ كل تقرير قابل للربط **مرئي أصلاً** للمنادي داخل المشروع. صفر تصعيد رؤية.

## الثغرات المكتشفة

### [CVE-S7-001] `order` بلا حد أعلى ⇒ 500 بدل 400
- **الخطورة:** LOW
- **الموقع:** `modules/finance/dto/index.ts` — `CreateBOQItemDto.order` / `UpdateBOQItemDto.order`
- **السيناريو:** `POST /projects/:id/boq` بـ `{"order": 2147483648}`. الـ DTO كان `@IsInt() @Min(0)` **بلا `@Max`**، والعمود `INTEGER` (INT4، حد أقصى 2,147,483,647) ⇒ القيمة تعدّي الـ validation وتنفجر في طبقة الـ driver.
- **التأثير:** خطأ غير معالَج (500) بدل 400 نظيف — إفشاء ضمني لطبقة التخزين + ضوضاء في السجلات. **كل حقل رقمي آخر في الـ module كان محدوداً؛ ده الوحيد اللي فلت.**
- **الإصلاح المطبق:** `ORDER_MAX = 1_000_000` + `@Max(ORDER_MAX)` على الحقلين.
- **الحالة:** FIXED-BY-HACKER ✅

### [CVE-S7-002] اسم بند من مسافات فقط
- **الخطورة:** LOW
- **الموقع:** `dto/index.ts` — `CreateBOQItemDto.name` / `UpdateBOQItemDto.name`
- **السيناريو:** `{"name": "   "}` يعدّي `@MinLength(1)`، والـ service بيعمل `.trim()` ⇒ **بند بقيمة تعاقدية واسمه سلسلة فارغة**.
- **التأثير:** بند شبح في الشجرة يحمل مالاً ولا يمكن تمييزه بصرياً؛ وسيلة إخفاء لبند مسعّر وسط قائمة.
- **الإصلاح المطبق:** `@Matches(/\S/)` على الاسم في الـ DTOين.
- **الحالة:** FIXED-BY-HACKER ✅

### [CVE-S7-003] تاريخ تقويمي مستحيل يُقبل ويُزحلَق بصمت
- **الخطورة:** **MEDIUM** (نزاهة بيانات على حقل يحكم قراراً مالياً)
- **الموقع:** `financial-settings.service.ts` — `buildDiff`، فرع `warrantyStartDate`
- **السيناريو (مُثبَت معملياً):**
```
2026-02-30   isISO8601: true   → new Date(...) → 2026-03-02
2026-04-31   isISO8601: true   → new Date(...) → 2026-05-01
2026-02-29   isISO8601: true   → new Date(...) → 2026-03-01   (سنة غير كبيسة)
2026-13-01   isISO8601: false  → مرفوض في الـ DTO ✅
```
`@IsDateString` يفوّض لـ `isISO8601` غير الصارم، وهو يفحص **نطاق الأرقام** لا **صحة التقويم**. الـ service كان بياخد الناتج كما هو.
- **التأثير:** المحاسب يُدخل تاريخ تسليم، فيُخزَّن **تاريخ آخر لم يكتبه أحد**، ويُبنى عليه `retentionReleased` (الإفراج عن الاحتجاز). والأسوأ: `warrantyStartDate` **غير قابل للمسح** (بند مفتوح رقم 2 عند المخطط) ⇒ التاريخ الخاطئ **دائم**. الـ audit يسجّل القيمة المزحلقة كأنها مُدخَل المستخدم ⇒ **سجل التدقيق نفسه يوثّق ما لم يحدث**.
- **الإصلاح المطبق:** تحقّق round-trip — `next.toISOString().slice(0,10)` لازم يطابق المُرسَل، وإلا `400 تاريخ بداية الضمان غير صالح`.
- **الحالة:** FIXED-BY-HACKER ✅

### [CVE-S7-004] فحص الأبناء غير مقيَّد بالمشروع (خرق نمط الـ session)
- **الخطورة:** LOW (defense-in-depth — غير مستغَلّ اليوم)
- **الموقع:** `boq.service.ts` — `softDelete`، استعلام `count`
- **السيناريو:** `count({ where: { parentId, deletedAt: null } })` كان **الاستعلام الوحيد في الـ module اللي بيقرر قراراً بدون قيد المشروع/المستأجر جوّه الـ where**. غير مستغَلّ حالياً لأن `sub-items` يشتق `projectId` من الأب، لكن **الـ FK لا يفرض تطابق المشروع** — أي كتابة مستقبلية (استيراد جماعي، سكربت ترحيل) تقدر تخلق ابناً بـ `projectId` مختلف، وساعتها الحارس يعدّ أبناءً أجانب (فيمنع حذفاً مشروعاً) أو يفوّت أبناءً حقيقيين (فييتّمهم).
- **الأهمية:** ده بالظبط النمط اللي الـ session جاية تقفله (قاعدة #5) — لقيته **جوّه كود الـ session نفسه**.
- **الإصلاح المطبق:** إضافة `projectId: current.projectId` للـ where.
- **الحالة:** FIXED-BY-HACKER ✅

### [CVE-S7-005] عمق شجرة BOQ غير محدود ⇒ تعطيل ذاتي دائم لـ GET /boq
- **الخطورة:** LOW (يتطلب دوراً مصرَّحاً + طلبات متكررة)
- **الموقع:** `boq.service.ts` — `persistNew` (مسار `sub-items`)
- **السيناريو:** `POST /boq/:id/sub-items` متكرر، كل مرة على البند المولود للتوّ ⇒ سلسلة بعمق N. البناء iterative (سليم)، لكن **تسلسل الرد recursive** (`JSON.stringify` + الـ TransformInterceptor) ⇒ عند عمق كافٍ كل `GET /boq` للمشروع يرجّع 500.
- **التأثير:** **الضرر لا رجعة فيه من ناحية القراءة** — مفيش endpoint يقدر يرجّع الشجرة عشان تتصلّح، وحتى الحذف لازم يبدأ من الورقة للأعلى (حارس الأبناء). تعطيل ذاتي دائم لمقايسة المشروع. الـ throttler (100/دقيقة) يبطّئ ولا يمنع.
- **الإصلاح المطبق:** `MAX_BOQ_ANCESTORS = 10` + `assertDepthWithinLimit` (مشي صاعد **جوّه الـ transaction**، والحلقة محدودة بالسقف نفسه فتنتهي حتى لو صار الدوران ممكناً يوماً).
- **الحالة:** FIXED-BY-HACKER ✅

### [CVE-S7-006] نفس التقرير يُربَط بعدد غير محدود من البنود ⇒ تضخيم الإنجاز
- **الخطورة:** **MEDIUM**
- **الموقع:** `boq.service.ts` — `linkUpdate` + `findTree` (حساب `completedPct`)
- **السيناريو:** الـ unique constraint هو `(boqItemId, updateId)` — يمنع تكرار **نفس الزوج** ولا يمنع ربط **نفس التقرير** بـ 50 بنداً. كل بند يحتسب **كامل** `update.cost`. `SITE_ENGINEER` (أدنى دور له صلاحية الربط) يقدر يخلي كل بنود المقايسة تعرض 100%.
- **التأثير:** `Σ completedValue` للبنود تتجاوز `totalCompleted` للمشروع بمضاعفات ⇒ العميل يرى إنجازاً وهمياً. **لا يمسّ المال:** `netDue` يُحسب من `Update.cost` مباشرةً ولا يمرّ على الـ BOQ إطلاقاً ⇒ **لا تحويل أموال، تضليل عرض فقط**. وهذا بالضبط سقف الخطورة.
- **الحالة:** **مفتوحة — لم تُصلَّح** ⚠️ (مبرر أدناه)

### [CVE-S7-007] الـ CLIENT محجوب عنه `contractValue` في الملخص ومكشوف له مُفصَّلاً في الـ BOQ
- **الخطورة:** **MEDIUM** (تناقض سياسة إفصاح)
- **الموقع:** `financial-summary.service.ts` (فرع CLIENT) مقابل `boq.service.ts` `findTree` + جدول صلاحيات الخطة
- **السيناريو:** `GET /financial-summary` يحجب عن الـ CLIENT الحقول الأربعة الداخلية ومنها `contractValue`. وفي نفس الوقت `GET /boq` **مسموح للـ CLIENT** ويرجّع `contractValue` **لكل بند** ⇒ جمع بسيط للجذور يعطي قيمة العقد (أو تقديراً وثيقاً)، بتفصيل أدق من المحجوب أصلاً.
- **التأثير:** الحجب في الملخص **ديكوري** ما دام الـ BOQ مفتوحاً. النتيجة أسوأ من أي الخيارين منفرداً: سياسة تبدو محكمة وليست كذلك، فيُبنى عليها قرار خاطئ لاحقاً.
- **الحالة:** **مفتوحة — لم تُصلَّح** ⚠️ (قرار سياسة، لا عيب كود — مبرر أدناه)

### [CVE-S7-008] `ensureProjectAccess` خارج الـ transaction (TOCTOU على الصلاحية)
- **الخطورة:** LOW
- **الموقع:** كل الـ write paths في `finance` (المرحلتان 4 و6)
- **السيناريو:** الـ session طبّقت بانضباط قاعدة "كل قراءة سابقة جوّه transaction الكتابة" — **على قراءات البيانات فقط**. قراءة **الصلاحية** (`ensureProjectAccess`) فضلت برّه. مهندس موقع تُسحب تعيينه أثناء تنفيذ طلبه يقدر يكمل كتابة واحدة بعد السحب.
- **التأثير:** كتابة واحدة بصلاحية منتهية، ضمن نفس المستأجر، **مسجَّلة بالكامل في الـ audit**. النافذة أجزاء من الثانية وتتطلب تزامناً مع فعل إداري.
- **الحالة:** **مفتوحة — لم تُصلَّح** ⚠️ (مبرر أدناه)

## 🔴 المحور 2 — `retentionPct = 100`: قراري

### **تُسجَّل ولا تُصلَّح — وليست NEEDS-CODER.**

**التحليل الهجومي (لماذا ليست ثغرة أمنية):**
1. **لا يوجد خصم مستفيد.** النظام نظام **المقاول**. `retentionPct = 100` تجعل `netDue ≤ 0` أي **تُظهر مستحقات شركة المشغّل نفسها صفراً**. لا يخدم مهاجماً خارجياً ولا يحوّل مالاً لأحد — أقرب لخطأ إدخال منه لهجوم.
2. **الحالة العكسية تُسقِط تصنيف "الثغرة".** `retentionPct = 0` تُضخّم `netDue`، وهي "إساءة" مكافئة تماماً ومتاحة لنفس الدورين. أي حدٍّ أفرضه على أحد الطرفين يترك الآخر مفتوحاً. **حدود النِّسبة مسألة تعاقدية لا مسألة بوابة.**
3. **الفعل مرصود بالكامل:** الـ audit يسجّل `retentionPct: 5 → 100` + الفاعل + الـ IP + الوقت، و`oldValues` مشتقة من الصف الفعلي. **قابل للتتبع والعكس.** معيار الأمان هنا هو الرصد لا المنع.
4. **صفر تصعيد صلاحية:** الفاعل `SUPER_ADMIN`/`ACCOUNTANT` — يفعلها بصلاحيته المشروعة، لا عبر خلل.

**ليه مش NEEDS-CODER:** NEEDS-CODER معناها ثغرة تحتاج **تغييراً معمارياً**. هنا لا يوجد ما يُصلَح معمارياً — المطلوب **رقم تعاقدي** لا يملكه لا الهاكر ولا المبرمج (هل السقف 10%؟ 20%؟ يختلف بالعقد وبالجهة). فرض رقم مخترع في الـ DTO كان هيكسر عقوداً مشروعة، وده ضرر أكيد مقابل خطر متخيَّل.

**توصيتي للمراجع الأعلى (قرار عمل):** لا حدّ في الـ DTO. بدلاً منه — عند ربط الـ frontend — **تحذير مرئي** عند `retentionPct > 10` أو عند `netDue ≤ 0` مع إنجاز موجب. المنع الصامت في الـ backend يخفي الخطأ؛ التحذير المرئي يخاطب الفاعل الحقيقي (المُدخِل).

## 🔴 المحور 3 — A-S7-4: غياب حارس المشروع الملغى

### **حكمي: فجوة اتساق موثَّقة — لا ثغرة. لا إصلاح في هذه الـ session.**

**الفحص:** `payments.service.ts:232` يمنع تسجيل دفعة على مشروع `CANCELLED`. `finance` يسمح بـ PATCH للإعدادات وبكل كتابات الـ BOQ على مشروع ملغى. `CANCELLED` حالة **نهائية** (`projects.service.ts:33`).

**لماذا ليست ثغرة:**
- الفارق الجوهري: منع الدفعات على مشروع ملغى يمنع **حركة نقدية جديدة**. تعديل إعدادات/مقايسة مشروع ملغى **لا يحرّك مالاً** — الـ summary قراءة محسوبة، والـ BOQ بيان كميات.
- **التسوية بعد الإلغاء حالة عمل حقيقية:** مشروع يُلغى في منتصفه ويحتاج ضبط قيمة العقد ونسبة الاحتجاز لتصفية المستحق. حارس صارم كان هيمنع إغلاقاً مشروعاً.
- كل كتابة مسجَّلة في الـ audit بالفاعل والوقت.

**ما هو خطأ فعلاً:** أن التباين **غير موثَّق**. القارئ التالي سيرى الحارس في `payments` وغيابه في `finance` ويستنتج سهواً.
**توصيتي:** تعليق صريح في `financial-settings.service.update` وفي `boq.service` يوثّق القرار (حركة نقدية ↔ بيان تخطيطي)، **لا حارس**. يُنفَّذ في أي جلسة لاحقة تمسّ الملفين — لا يستأهل فتح المرحلة 4/6 من جديد.

## 🔴 المحور 5 — إعادة الهجوم على أنماط الـ session (قاعدة #5)

الـ session تقفل نمطين. أعدت مهاجمة **كل** كود الـ session ضدهما — والنتيجة: **خرق واحد لكل نمط**.

**النمط أ — "القيد جوّه الـ query لا بعد الجلب":**
| الاستعلام | مقيَّد؟ |
|---|---|
| `readSettings` (settings) | ✅ عبر `project: { companyId, deletedAt }` |
| `readItemIn` (BOQ) | ✅ |
| `findTree` — البنود | ✅ |
| `findTree` — الروابط | ✅ (نفس مجتمع المرحلة 5) |
| `getSummary` — الـ updates | ✅ عبر `phase.project` |
| `getSummary` — الـ payments | ✅ |
| `linkUpdate` — الـ update | ✅ (الطبقة 4) |
| **`softDelete` — عدّ الأبناء** | ❌ **خرق** ⇒ CVE-S7-004 (أُصلح) |

**النمط ب — "القراءة السابقة جوّه transaction الكتابة":**
| المسار | القراءة جوّه الـ tx؟ |
|---|---|
| Settings PATCH | ✅ |
| BOQ create / sub-item (إعادة تأكيد الأب) | ✅ |
| BOQ PATCH | ✅ |
| BOQ delete (البند + الأبناء) | ✅ |
| link-update (البند + التقرير + الرابط القائم) | ✅ |

## ثغرات لسه مفتوحة (مع مبرر)

**CVE-S7-006 (MEDIUM) — تضخيم الإنجاز بربط التقرير بعدة بنود.**
الإصلاح الحقيقي = **توزيع نسبي** (نسبة/مبلغ لكل رابط) وده **تغيير schema** (عمود على `BOQItemUpdate`) + تغيير عقد الـ API + تعديل المرحلتين 5 و6 — نطاق session كاملة، والخطة اختارت صراحةً "روابط مباشرة بلا rollup". **سقف الضرر عرضي بحت** (`netDue` لا يمرّ على الـ BOQ إطلاقاً). لا أفرض حلاً معمارياً من داخل دور الهاكر على قرار خطة معتمد. **يُرفع للمخطط/المراجع كبند جلسة قادمة.**

**CVE-S7-007 (MEDIUM) — تناقض إفصاح `contractValue`.**
الخياران المتاحان **كلاهما قرار عمل لا كود:** (أ) حذف `CLIENT` من `GET /boq` — نقض لجدول صلاحيات معتمد في الخطة؛ (ب) إعادة `contractValue` للـ CLIENT في الملخص والاعتراف بأن المقايسة مكشوفة له أصلاً (وهو العُرف الشائع: بيان الكميات يُسلَّم للعميل مع العقد). **ترجيحي (ب)** — الحجب الحالي يعطي أماناً موهوماً. لكن أياً منهما نقض لقرار الخطة ⇒ **قرار المراجع الأعلى، لا الهاكر.**

**CVE-S7-008 (LOW) — TOCTOU على الصلاحية.**
الإصلاح يستلزم `ensureProjectAccess` بنسخة تقبل `TransactionClient` — تعديل في `projects.service.ts` يمسّ **كل** مستهلكيه (payments/comments/updates/chat/media). **كلفة blast-radius أعلى بكثير من الخطر** (نافذة أجزاء من الثانية، داخل نفس المستأجر، مسجَّلة بالكامل). **مقبول بوعي**، يُوثَّق في الـ BACKLOG.

**بنود أدنى من عتبة الـ CVE (مرصودة للسجل):** لا `Idempotency-Key` على `POST /boq` (تكرار ينشئ بنداً مزدوجاً — مرئي وقابل للحذف، بخلاف الدفعات)؛ لا `unlink` لرابط خاطئ؛ لا مسح لـ `warrantyStartDate` (يضاعف أثر CVE-S7-003 المُصلَّح)؛ `linkUpdate` عند سباق `P2002` يرجّع `id: null`.
